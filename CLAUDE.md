# fab-shop

Vertical SaaS for quoting, job-tracking, and invoicing for small custom/ornamental/mobile metal fabrication and welding shops (1-8 people) — replacing the QuickBooks-plus-spreadsheets-plus-paper-traveler status quo.

## Tech stack

- Laravel 13 (PHP 8.3+), Inertia.js + React + TypeScript, Tailwind CSS
- PostgreSQL, single database, shared schema
- Pest for testing, Pint for code style

## Local development (Sail)

The app runs via Laravel Sail (Docker), not the host PHP — `.env`'s `DB_HOST=pgsql`/`MAIL_HOST=mailpit` only resolve inside Sail's Docker network, so bare `php artisan` / `npm` on the host will fail to connect. Use `./vendor/bin/sail artisan ...`, `./vendor/bin/sail npm ...`, `./vendor/bin/sail test`, etc. (alias `sail` to `./vendor/bin/sail` for less typing). Bring the stack up with `./vendor/bin/sail up -d`.

Services: `pgsql` (Postgres, matches production, default port 5432), `redis` (queue backend for Horizon), `mailpit` (catches all outgoing mail — inbox UI at `http://localhost:8025`), `horizon`, `scheduler`, and `reverb` (all below). App runs at `http://localhost` (port 80).

The test suite also runs against a real Postgres `testing` database (via `phpunit.xml`), not sqlite — so `./vendor/bin/sail test` needs the `pgsql` container up. Tests force `QUEUE_CONNECTION=sync` and `CACHE_STORE=array` (also in `phpunit.xml`), so they never touch Redis or Horizon.

**Queue worker:** the `horizon` service runs `artisan horizon` as its own container (overriding Sail's default entrypoint, same image) and starts automatically with `./vendor/bin/sail up -d` — quote PDF generation/email (F2) and any future queued work just processes on its own, no manual `queue:work` needed. Dashboard at `http://localhost/horizon` (gated by `HorizonServiceProvider::gate()` outside local env). `QUEUE_CONNECTION=redis` — Horizon only supports Redis.

**Scheduler:** the `scheduler` service runs `artisan schedule:work` the same way (own container, overridden entrypoint) so `routes/console.php`'s `Schedule::command(...)` entries (currently just `app:notify-expired-trials`, hourly - a trial ends 14 x 24h after signup, at any time of day) actually fire without a real cron. `schedule:work` polls once a minute and re-evaluates every registered schedule; check what's due with `./vendor/bin/sail artisan schedule:list`.

**Reverb** (job board live updates, F3) runs the same way — its own `reverb` container (entrypoint overridden to `artisan reverb:start`), port 8080. Job board broadcasts use `ShouldBroadcastNow` specifically so they don't *need* a queue worker, but Reverb itself still has to be running to accept the WebSocket connection, which it now is by default.

Splitting Reverb into its own container broke server-to-server broadcasting until it was caught and fixed: `REVERB_HOST=localhost` is right for the *browser* (it connects through the port Docker forwards to the host), but this app also has to push events to Reverb itself when something happens (`broadcast(...)`), and from inside the `laravel.test` container "localhost" no longer means anything - Reverb is a separate container now. Fixed with a second env var, `REVERB_INTERNAL_HOST=reverb` (the Docker service name), which `config/broadcasting.php`'s `reverb` connection uses for its `host` option instead of `REVERB_HOST`; the browser-facing `VITE_REVERB_HOST` is untouched. Because `JobBoardUpdated` is `ShouldBroadcastNow`, a broken connection here throws mid-request - the status *does* still save (the DB update happens before the broadcast call), but the request comes back as a 500. If that happens again, check `storage/logs/laravel.log` for a Pusher/cURL connection error before assuming the state machine itself is broken.

`./vendor/bin/sail artisan storage:link` is required once per environment for anything served off the `public` disk (job photos) — quote PDFs don't need it since they're streamed through a controller route instead.

### Demo data

`demo:seed-team` and `demo:seed-multi-shop` build realistic, fully interconnected data for manual testing — a shop with a full team + catalog (incl. tooling - the same 1/4in bit for steel and for aluminum) + an in-progress job, plus six months of invoiced jobs and open/stale/lost quotes so the dashboard has real numbers (first command), and two isolated shops plus a user who belongs to both, to click through tenant isolation and the shop switcher (second command). Both print login credentials (password `password` for every seeded user) and accept `--fresh` to replace their own data on a rerun.

Both refuse to run unless `APP_MODE=demo` is set (on top of a non-production `APP_ENV`) — two independent gates, so a stray env misconfiguration can't run them somewhere real data lives. `APP_MODE` is separate from `APP_ENV` on purpose: local dev without `APP_MODE=demo` set still refuses to run these.

### QuickBooks Online sync (F4)

**Currently switched off - a "future feature".** `Feature::QuickbooksSync->isShipped()` returns false, so the `/quickbooks/*` routes aren't registered, the nav entry is removed, `JobStatusController` doesn't dispatch `PushJobInvoiceToQuickBooks`, and the feature is hidden from the marketing page and plan/add-on pickers. The code, tables and permissions are all still in place; the QuickBooks tests skip themselves while it's off. To re-enable, flip it to `true` in `Feature::isShipped()` and re-add the nav item in `AuthenticatedLayout.tsx`. The rest of this section describes the integration as built.

Built without real Intuit credentials - `QUICKBOOKS_CLIENT_ID`/`QUICKBOOKS_CLIENT_SECRET` are blank in `.env`/`.env.example`, so the OAuth connect button currently redirects to a real Intuit URL that can't complete the handshake. Everything downstream of that (token exchange, refresh-on-expiry, customer dedupe, invoice push/retry) is built and tested against `Http::fake()` in `tests/Feature/QuickBooksConnectionTest.php` and `QuickBooksInvoiceSyncTest.php` - covers the three acceptance cases from `docs/product-desc.md`'s F4 section (token expiry mid-sync, dedupe not duplicate, retry not silently drop) - but has never round-tripped against a real sandbox company.

To wire up real credentials: register a free app at [developer.intuit.com](https://developer.intuit.com), grab its sandbox Client ID/Secret, set `QUICKBOOKS_CLIENT_ID`/`QUICKBOOKS_CLIENT_SECRET` in `.env`, and add `http://localhost/quickbooks/callback` as the app's redirect URI in Intuit's dashboard (must match `QUICKBOOKS_REDIRECT_URI` exactly). `QUICKBOOKS_ENVIRONMENT=sandbox` talks to a different API base URL than production, not just a header/param switch - flip it deliberately, not as an afterthought.

`App\Services\QuickBooks\QuickBooksClient` is built directly on Laravel's `Http` facade rather than the official `quickbooks/v3-php-sdk` - that package has its own HTTP internals that bypass `Http::fake()`, which would have made the acceptance-case tests much harder to write without a live sandbox company.

`Job->quickbooks_sync_error` holds the last failure message if a push failed - check it (or the job in Horizon's Failed tab once `$tries` is exhausted) before assuming QuickBooks sync silently isn't happening.

## Deployment (Railway)

Production runs on Railway from the root `Dockerfile` (one image, four services - web/horizon/scheduler/reverb - differing only in start command), with Postgres, Redis and an S3-compatible bucket. The whole project is Railway IaC in `.railway/railway.ts` (`railway config plan`/`apply`, run from CI on merge); app code deploys on push to `main`. Don't add `railway.json` files - IaC can't manage services that have them. Full setup and variable list: [docs/deploy-railway.md](docs/deploy-railway.md). Two things differ from Sail and matter when changing code: services don't share a filesystem, so anything written by one process and read by another (job photos, quote PDFs, CSV import uploads) must go through the default/media disk - never `Storage::disk('local')->path()` or `Media::getPath()` - and photo URLs go through `JobController::photoUrl()` (signed URL on S3). Reverb has separate browser (`REVERB_HOST`/`PORT`/`SCHEME`) and server-to-server (`REVERB_INTERNAL_*`) settings.

## Multi-tenancy (critical)

Every tenant-owned table carries a `shop_id`. Tenant isolation is enforced exclusively through the `BelongsToShop` trait + Eloquent global scope, keyed off the authenticated user's *current* shop (`users.current_shop_id`) — never their full membership list. Never add `->where('shop_id', ...)` manually at a call site — the global scope is the only thing that guarantees no cross-tenant leak. Every new tenant-owned model needs a cross-tenant-isolation test (a user from Shop A must not be able to read/write Shop B's records).

Shop membership is many-to-many (`shop_user` pivot) — a user can belong to several shops, a shop can have several users, and each shop has exactly one owner (`shops.owner_id`). Roles (Owner/Admin/Staff) are assigned per shop via Spatie permission's teams feature, keyed on `shop_id`, so the same user can hold different roles in different shops. A member of more than one shop gets a shop switcher in the nav (`ShopSwitchController`, `POST /current-shop/{shop}`) that flips `current_shop_id` after checking membership — nothing else about tenant scoping changes, since everything already keys off that column.

## Permissions (per shop)

Access is granted per resource and action: permission names are `{resource}.{action}` (e.g. `quotes.delete`, `jobs.cancel`, `financials.view`), defined in `App\Enums\ShopResource` (resources, their actions, and a plain description of what each action really allows). `App\Support\ShopPermissions` holds the full list and each role's out-of-the-box grants (`defaultsFor()`); `seedRoles($shop)` creates a shop's roles with those defaults - called at signup, by the demo commands, and by the test helper. Each permission is also a Gate ability of the same name, so routes use `can:quotes.delete` middleware; resource controllers get theirs from the `AuthorizesShopResource` trait (edit pages need only `view` and render read-only without `update`).

Resolution (`User::shopPermissions()`): the Owner role has everything → otherwise the role's grants in the current shop → then per-member overrides on `shop_user.permission_overrides` (true = allow, false = deny, absent = inherit). Any action on a resource implies `view` of it. Spatie's own `Gate::before` permission check is **disabled** (`permission.register_permission_check_method = false`) - left on, it approved anything the role granted before our gates ran, silently ignoring per-member denies.

Markup (`markup.view`/`markup.update`) is Owner-only by default - Admin and Staff don't get it from their role, only via a per-member override. On a quote, the markup % input is hidden without view and read-only without update, and `QuoteController::syncLineItems()` ignores a submitted markup from anyone without update (an existing line keeps its markup, a new or retyped one gets the shop default); quote history strips markup figures for those who can't view it.

Who can change access: editing *role* defaults is Owner-only (`manage-shop` gate, never delegable). Per-member access needs `team.manage-access` (Admins by default), with guard rails in `TeamMemberAccessController`/`UpdateTeamMemberAccessRequest`: nobody edits the owner or themselves; only the owner changes roles or edits an Admin; a non-owner can only *allow* permissions they hold themselves. Adding a permission = add the action to `ShopResource`, decide `defaultsFor()`, and add a migration that calls `ShopPermissions::seedRoles()` for existing shops (it only adds grants, never revokes).

Deletes that would orphan history are refused with a flash `error` instead of hitting the database's restrict constraint (a customer with quotes/jobs; a quote that became a job - archive it instead). Catalog deletes are fine: quote lines keep their description and price, only the link is nulled.

Gate financial data on the server, not just in the UI - e.g. the dashboard omits the `financials` prop entirely without `financials.view`, since Inertia props are readable in page source. `SetPermissionsTeamFromCurrentShop` must run before `HandleInertiaRequests` (it does, in `bootstrap/app.php`) so the shared `auth.permissions` list is resolved against the current shop; the frontend checks it with `useCan()` (`resources/js/lib/permissions.ts`) purely to hide controls.

## Pictures and documents

`App\Support\Images` is the one way a record gets a picture: a single Spatie-media file per record (`singleFile()` collection), JPG/PNG/GIF/WebP only (no SVG - it can carry script), 5 MB max, with a synchronous 256px square `Fit::Crop` conversion, so everything displays as a square (circle-masked for people and logos). User avatar (`avatar`), customer and business partner logo (`logo`), material photo (`image`). Files are streamed through the app (`users.avatar`, `customers.logo`, `business-partners.logo`, `materials.image`), never linked to the disk, so access follows tenancy and works on S3 - a user's avatar is only visible to themself and members of their current shop; the catalog images load for anyone who can see that resource *or* quotes/jobs (`EntityImageController`), since a logo shows wherever the name does. The URL carries `?v={media id}` so it can be cached hard. Forms post the file as `logo`/`image` plus a `remove_*` flag; updates are a POST spoofing PUT (`_method`) because PHP doesn't parse multipart PUT bodies. Lists must eager-load `media` before calling `avatarUrl()`/`logoUrl()`/`imageUrl()` or they N+1. Frontend: `Avatar.tsx` (`UserAvatar` initials fallback, `LogoAvatar` building icon, `SquareImage`) and `ImageField.tsx`.

Certifications can carry up to 3 documents (PDF or image, 30 MB each, `App\Support\CertificationDocuments`), uploaded live on a saved record (`certifications.documents.*`) or with the create form; the list shows a paperclip and count. Reuses `Attachments` for thumbnails and serving.

## Material types and tooling

`material_types` are per-shop records: every shop gets the built-ins in `App\Support\MaterialTypes::DEFAULTS` (via a `Shop::created` hook, so signup, demo data and test factories all have them; `is_default`, can't be renamed or deleted) and may add custom ones up to `config('shop.max_custom_material_types')` (20). Names are unique per shop case-insensitively (a `lower(name)` index). A catalog `Material` has one optional type; a `Tool` is rated for one or more (`material_type_tool`). A type still used by a tool or material can't be deleted - the controller explains, and the FK (no cascade) backs it up. The quote builder warns (advisory, client-side) when a tooling line's tool is rated for none of the quote's material types. To add a built-in, append to `DEFAULTS` and run `MaterialTypes::seedDefaults()` for every shop in a migration (it's idempotent).

## Job board stages and moves

The board's columns are shop-configurable, not a fixed enum. `job_stages` is a per-shop, ordered (`position`) list: `App\Enums\JobStageRole` marks exactly three fixed rows - `NotStarted` (first), `Shipped`, `Invoiced` (last two) - that always exist and can't be renamed, reordered, or deleted (enforced server-side: `UpdateJobStageRequest::authorize()` blocks renaming a built-in, `JobStageController::destroy()` blocks deleting one). Everything between them is the shop's own custom stages (`role` null) - add/rename/delete/reorder from `/job-stages`, gated by the `job-stages.*` permissions (`ShopResource::JobStages`). Every shop starts with one generic starter stage, `App\Support\JobStages::STARTER_STAGE_NAME` ("Setup") - deliberately not named after a real fabrication step (a shop's actual process varies too much to presume: one cuts on a bandsaw, another on a CNC, neither of which is "welding"). `App\Support\JobStagePositions::renumber()` is the one place `position` values get assigned (a full renumber of the shop's custom stages on every create/reorder/delete) - no unique DB constraint on position, since app-level consistency is enough and a two-phase shuffle to satisfy one mid-reorder isn't worth it.

`Job::canTransitionTo(JobStage $target)`: any stage with a higher `position` is a legal forward move - skipping a stage a job doesn't need is allowed on purpose, not just single-step - and a backward correction is legal only while the job's current stage isn't `Shipped`/`Invoiced`. Cancellation isn't a stage any more - `Job::cancelled_at` (nullable timestamp, not fillable - set only via `JobStatusController::cancel()`, same pattern as `suspended_at`/`onboarded_at`) is a side flag orthogonal to whatever stage the job was at, so a cancelled job keeps its last real position instead of losing it to a terminal enum case. Reaching the `Shipped`-role stage flags a job as ready-to-invoice on the dashboard; reaching the `Invoiced`-role stage triggers the QuickBooks push (`PushJobInvoiceToQuickBooks`) and sets `invoiced_at` - both keyed off `JobStageRole`, never a stage's name, so renaming a stage can't break either.

Every status change - button or drag - goes through `JobMoveDialog` for confirmation first. Drag-and-drop (`@dnd-kit/core`, drag handle only so card links and touch-scrolling still work) is a per-shop setting, `shops.job_board_drag_enabled`, off by default (`config('shop.defaults.job_board_drag_enabled')`); the board only enables it for users with `jobs.update`. Moving needs `jobs.update`, cancelling `jobs.cancel` - checked in `JobStatusController` (a single `PATCH jobs/{job}/status` endpoint, `job_stage_id` for a move or `cancel: true` for cancellation, never both) since it depends on which one the request is.

## Material & scrap tracking (F5)

`JobMaterialUsage` is the actual-consumption ledger, deliberately separate from `QuoteLineItem` (the estimate a job's price is fixed to - see `Job::total`'s own note): it only ever grows, so reversing a job's status never erases the cost of what was already used or scrapped, per the F3 design decision this fulfills. `type` (`App\Enums\MaterialUsageType`: `Used`/`Scrap`) keeps waste visible on its own rather than folded into "used." `Job` gets computed (never stored) `estimated_material_cost` (sum of the quote's `material`-type lines' `cost` - shop's cost, pre-markup, not what the customer is charged), `actual_material_cost`, `scrap_cost`, and `material_cost_variance` (actual + scrap - estimated; positive means the job cost more material than quoted).

Gated by the `material-tracking` feature (`Feature::MaterialTracking`, now `isShipped() => true` - Start-up doesn't include it, Pro does, trial gets everything) on top of `job-board` and `jobs.update` (no separate permission - logging usage is part of working the job, same scoping as job photos). `JobController::show()` omits the `materialTracking` prop entirely for a shop without the feature, same "don't send what they're not entitled to" rule the dashboard's `financials` prop follows - it's not just hidden client-side. Logging or removing an entry also writes a normal `activity()` log entry on the job, so it shows up interleaved with status changes in the existing History panel - job photo uploads also log (one entry per upload, with file names; deleting a photo doesn't), as do due-date changes and the due date a job inherits at conversion.

The material picker's "suggested cost" is the material's cheapest known `businessPartners` price, purely a starting point - always overridable, since the entire point of tracking *actual* cost is that it can differ from any predicted default.

## Qualification records (F7)

Built generalized, not welding-specific, despite the original spec's WPS/PQR/welder-cert framing - a fab shop's compliance surface also covers things like NDT inspection or equipment operator cards, and nothing here assumes welding. `Feature::QualificationRecords` (`qualification-records`) is the renamed `WeldRecords`/`weld-records` case - safe to rename outright since it had never shipped.

Three models: `Procedure` (a shop-defined process people get qualified against - a catalog resource like `Material`/`Tool`, case-insensitive unique name per shop, can't be deleted while a `Certification` or `JobQualificationRecord` references it, same restrict-by-default FK convention as `MaterialType`), `Certification` (a person's qualification - `user_id` required, `procedure_id` optional since plenty of real certs aren't tied to a shop-defined procedure, `expires_at` nullable meaning "never expires"), and `JobQualificationRecord` (the job-level ledger, only ever grows, same reasoning as `JobMaterialUsage` vs. `QuoteLineItem`).

`JobQualificationRecord::was_qualified` is a **snapshot**, not a live check: `JobQualificationRecordController::wasQualified()` computes it once, at logging time, from whether `performed_by` held a `Certification` covering `procedure_id` as of `performed_at` (`Certification::coversOn()`) - never recomputed, so a certification expiring later doesn't retroactively flag work that was compliant when it happened. Null when no procedure was selected. Watch for the array-access trap this hit once already: `procedure_id` is nullable and can be *entirely absent* from `$request->validated()` (not just null) when the request omits it - index it with `?? null`, not a bare `$data['procedure_id']`, or a missing key throws instead of evaluating falsy.

Gated by the `qualification-records` feature on top of `jobs.update` for logging (no separate permission, same as material tracking); `procedures.*`/`certifications.*` are their own catalog permissions (Admin full CRUD, Staff view-only by default) for the `Procedure`/`Certification` catalog pages themselves. `JobController::show()` omits the `qualificationRecords` prop entirely without the feature, same pattern as `materialTracking`.

Document attachments (the actual WPS/PQR/cert file) are **not built** - deferred on purpose, see `docs/product-desc.md`'s F7 section for why and what to add when it's picked back up.

## CSV import (F9)

One mechanism shared by seven resources (Customers, Materials, Services, Business Partners, Equipment, Tooling, Material types) rather than one per resource - see `App\Support\CsvImport\`. `ResourceImporter` is the abstract shape each resource implements: its template columns, how a raw row resolves into model attributes (including name-based relational lookups - `material_type` on Materials, a `;`-separated `cuts` list on Tooling - resolved against the shop's own records, never auto-created), and the validation those attributes must pass. `ImporterRegistry` maps a route's `{resource}` key to one. Owner-only (`can:manage-shop`), gated per-resource by the same `Feature` each resource's own pages already require.

Processing is queued (`ProcessCsvImport`) - the upload endpoint returns the new `Import` row's id as plain JSON (not an Inertia redirect, since `CsvImportDialog.tsx` stays open on the current page rather than navigating), and the dialog polls `GET /imports/status/{import}` (also plain JSON) until status leaves `pending`. A row is matched to an existing record by case-insensitive `name` - matched, checkbox off, it's skipped; checkbox on, its fields are replaced. That dedupe check also looks at what the *same import run* has already created/updated (not just the database), so two rows in one file with the same name, however they differ in case, resolve as one record. A header missing a required column fails the whole file before any row is touched; one bad row among valid ones is reported by row number while the rest still import.

Console/queue context has no authenticated user, so - like the demo commands and `NotifyExpiredTrials` - every query inside `ProcessCsvImport` filters by shop_id explicitly; the tenant global scope is a no-op there. Watch for the same silent-mass-assignment trap `Invitation::accepted_at` hit: `Import`'s count/error columns must be in its `$fillable` list, or `$import->update([...])` on them does nothing and the row's `status` field is the only thing that visibly changes.

## Frontend formatting

`.prettierrc` matches the repo's style (single quotes, 4 spaces). Much of the existing code was hand-formatted rather than Prettier output, so format only files you create or substantially rewrite - running Prettier over the whole tree reflows lines in files you never touched.

## UI components and theming

Tailwind v4 (CSS-first: no `tailwind.config.js`, all theme tokens in `resources/css/app.css`, wired in through `@tailwindcss/vite`) plus shadcn/ui (Radix + Tailwind, copied into `resources/js/Components/ui/` - `components.json` configures it; add components with `npx shadcn@latest add <name>`). Run npm on the host, not Sail: `node_modules` holds macOS native binaries. Two things to know after every `shadcn add`: it writes `import { cn } from "cn"` (fix to `@/lib/utils`: `sed -i '' 's#from "cn"#from "@/lib/utils"#' resources/js/Components/ui/*.tsx`), and it can prompt to overwrite shared files (`--overwrite` is safe for ones you haven't edited - `card.tsx`, `badge.tsx` and `alert.tsx` are customized here: no flex/padding on `Card`, and `success|warning|danger|info` variants on `Badge`/`Alert`). `ui/` is generated style (double quotes, no semicolons) - don't Prettier it.

Theming is one place: `--surface`/`--box`/`--ink` in `:root`/`.dark` in `app.css`; the shadcn tokens (`--background`, `--card`, `--primary`, `--sidebar`...) are defined *in terms of* those, so shadcn components and the older plain `bg-white`/`text-gray-*` markup (repointed at the same variables in the `@layer utilities` block) always agree. New markup should use semantic tokens (`bg-background`, `bg-card`, `text-muted-foreground`, `bg-success`...), not gray/white. The old `Components/` atoms (`PrimaryButton`, `SecondaryButton`, `DangerButton`, `TextInput`, `InputLabel`, `Modal`, `Dropdown`, `SearchableSelect`, `FlashToast`) are kept as thin API-stable wrappers over shadcn (`Button`, `Input`, `Label`, `Dialog`, `DropdownMenu`, `Popover`+`Command`, Sonner) so call sites don't change; `Checkbox` is shadcn's directly (`onCheckedChange`, not `onChange`). Headless UI is gone. The authenticated shell is shadcn `Sidebar` (`AuthenticatedLayout.tsx`); the nav item arrays (feature gating, permissions) are unchanged from the old top nav.

## Shop settings and timezones

Per-shop settings (`shops.timezone`, `stale_quote_days`, `win_rate_window_days`) are nullable; null means "use `config('shop.defaults.*')`", read through `Shop::localTimezone()` / `staleQuoteDays()` / `winRateWindowDays()` - never the raw column.

Everything is stored in UTC. Anything that depends on the shop's calendar (month boundaries, "today", dates shown to people, invoice dates) goes through `Shop::localNow()` / `localTimezone()`; the frontend formats timestamps with `useShopDateTime()` (`resources/js/lib/datetime.ts`), which uses the shared `shop.timezone` rather than the viewer's browser. The trial window is the deliberate exception: `trial_started_at`/`trial_ends_at` are fixed UTC instants set at signup (`Shop::TRIAL_DAYS` x 24h), never derived from the timezone, so changing timezone can't lengthen a trial. Two traps, both hit while building this:
- Call `->utc()` before assigning a shop-local Carbon to a model attribute - Eloquent stores the wall-clock digits and drops the offset.
- Call `->copy()` before `->setTimezone()` on a model's date attribute - Carbon dates are mutable, so converting in place changes the attribute and a later `save()` writes the local time as if it were UTC.

## Signup and onboarding (F8b/F8c)

Registration (`RegisteredUserController`) creates only the `User` - no `Shop` row. `User implements MustVerifyEmail` (the base `Authenticatable` class already provides the trait's `hasVerifiedEmail()`/`markEmailAsVerified()` unconditionally; the interface is the only thing the framework's `verified` middleware and `EmailVerificationPromptController` actually gate on) and the framework itself wires `Registered -> SendEmailVerificationNotification` for any `MustVerifyEmail` user (`EventServiceProvider::configureEmailVerification()`) - don't register it again in `AppServiceProvider`, that sent every signup two emails. A verified user with no shop, or whose shop hasn't finished onboarding, is redirected by the `onboarded` middleware (`EnsureShopIsOnboarded`, alias only - not global) to `/onboarding`; it's applied to `/dashboard` and the big authenticated route group in `routes/web.php`, deliberately never to the onboarding routes themselves (`auth`+`verified` only) or to `/`, `/invitations/*`, `/login`, `/register`.

`shops.onboarded_at` (null while mid-wizard) + `shops.onboarding_step` (`'team'` | `'catalog'` | null) drive `OnboardingController::show()`, which renders whichever step comes next - each step's own POST persists immediately (`storeShop`/`storeTeam`/`storeCatalog`), so refreshing mid-wizard resumes rather than loses progress. `ShopFactory` and the demo seed commands default to `onboarded_at => now()` (already-set-up shops) - only real signups start with it null. Steps 2 and 3 are skippable; a blank row (email or name) in either is dropped server-side before validation rather than rejected, since `useForm`'s `setData()` is async and can't be filtered-then-posted in the same handler (see `TeamStep.tsx`'s comment) - `router.post()` with an explicit literal payload is used for "Skip", not `useForm`'s own `post()`.

Team invites are `App\Models\Invitation` (`shop_id`, `email`, `role`, `token`, `expires_at`, `accepted_at`) - deliberately **not** `BelongsToShop`-scoped, since whoever looks one up by token isn't a member of that shop yet (and may be signed into a *different* one already); the token itself is the access boundary. `App\Actions\SendShopInvitation` creates/refreshes the row (`updateOrCreate` on `[shop_id, email]`, so re-inviting refreshes one row) and sends `ShopInvitationSent` via an on-demand route (`Notification::route('mail', $email)->notify(...)`), not `->notify()` on a `User`, since the invitee usually has no account yet. Used by both onboarding's team step and Team page's own "Invite by email" (owner-only via `manage-shop`, not the delegable `team.manage-access` - inviting grants shop access, not just an editable setting).

`InvitationController` (public, no `auth`/`guest` middleware - every auth state is handled explicitly) resolves one of five modes: `accepted`, `expired`, `ready` (already signed in as the invitee), `login-required` (an account exists, needs a password), `create-account` (no account yet). Accepting sets the joining user's `current_shop_id` to the invited shop and assigns the invited role there via Spatie's team context - never touches any other shop they belong to. A newly-created account is marked `email_verified_at` immediately (clicking the mailed link is itself proof of ownership) via direct assignment, not mass assignment - `email_verified_at` isn't in `User`'s `#[Fillable(...)]` list, same reasoning as `current_shop_id`.

## Platform admin console (F10)

Internal, cross-tenant staff tooling - entirely separate from the per-shop Owner/Admin/Staff roles. Gated by `users.is_platform_admin` (not fillable, not settable from any form - grant it via `php artisan app:grant-platform-admin {email}` or `forceFill` in tinker only) via a dedicated `platform-admin` Gate, checked with `can:platform-admin` route middleware. `PlatformAdminController`'s routes (`/platform-admin/*`) deliberately skip the `active`/`onboarded` middleware the rest of the authenticated app requires - platform staff aren't acting within a shop here, and may not belong to one at all. `PlatformAdminLayout.tsx` is a separate, minimal layout for this reason (`AuthenticatedLayout`'s nav assumes a current shop throughout).

The shop directory reads every `Shop` with no tenant filtering - the one legitimate cross-tenant read in the app, since `Shop` is the tenant record itself, not a `BelongsToShop`-scoped one. Two moderation actions: suspend (`shops.suspended_at`, nullable, not fillable - set only via `forceFill` in the controller, same pattern as `onboarded_at`) and an admin-initiated plan change that bypasses the shop's own Owner-only plan-pick UI. A suspended shop's members hit a new `EnsureShopIsActive` middleware (alias `active`, applied alongside `onboarded`) that redirects them to `/shop-suspended` - a plain notice, not a 403, since suspension is a moderation state to explain rather than a request they got wrong.

Potential revenue (active MRR vs. trial-potential MRR, both computed from `plans.monthly_price_cents` x shop counts, excluding suspended shops) is explicitly **not** real collected revenue - no Stripe/Square/Plaid integration exists. `monthly_price_cents` didn't exist on `Plan` before this and is seeded with placeholder numbers (Free $0, Start-up $49, Pro $99) pending an actual pricing decision. Also still open: no audit logging of what a platform admin viewed or changed, and no written internal-access policy - both flagged as needed before this touches real shop data, not just implementation follow-ups. See `docs/product-desc.md`'s F10 section for the full design note.

## Legal pages and consent records

Public pages `/terms`, `/privacy` and `/sms-terms` (`LegalController`, `Pages/Legal/*`) - linked from the marketing page footer, `GuestLayout` (login/register), the invitation page, onboarding, the in-app footer (`AuthenticatedLayout`) and the shared mail footer (`resources/views/vendor/mail`). Who the documents are *from* (company name/address/contact, governing law) comes from `config/legal.php` via `LEGAL_*` env vars; unset values render as bracketed placeholders, so nothing placeholder-ish ships unnoticed. The wording is a drafted starting point, not legal advice - have counsel review it before launch.

`consent_records` is an **append-only** audit trail (`ConsentRecord` throws on update/delete; withdrawing = a new `granted = false` row): who (user/shop FKs are `nullOnDelete`, with `subject_email`/`subject_phone` kept), which `ConsentType` (terms / privacy / sms), the document `version` (from `config/legal.php` - bump it whenever the document or checkbox wording changes), the *exact wording shown*, source, IP and user agent. It is deliberately not `BelongsToShop` (registration happens before a shop exists and no tenant should read it) and has no UI. Record through `App\Support\Consent`, which also owns the checkbox strings (`AGREEMENT`, `smsOptInText()`) - the frontend is given those strings, never retypes them, so the stored text can't drift from what was on screen.

Registration and invitation-accept (new account) require the `accepted_terms` checkbox (`TermsAgreement`) and call `Consent::recordAgreement()`. SMS is **prepared, not live**: `SmsConsentCheckbox` + `Consent::recordSms()/hasSmsConsent()` exist for whichever form first collects a mobile number (must be its own unchecked, optional checkbox - never bundled with the Terms, never a condition of purchase), and the SMS Terms/Privacy pages carry the A2P 10DLC language (program, frequency, rates, STOP/HELP, no sharing of mobile opt-in data). Users who registered before this existed have no recorded acceptance; a re-acceptance gate on version bumps is not built.

## Plans and pricing

Launch prices (hypotheses, not market-validated), defined once in `PlanSeeder`: Solo $29 (1 seat), Shop $59 (4 seats; the plan's key is still `start-up`, only its display name changed), Pro $119 (10 seats). Job board, quote history and AI quote drafting start at Shop; material tracking, qualification records and `Feature::AiAgent` (MCP access) are Pro, with the first two also sold as $25 add-ons. The default trial is 30 days (`PlatformSetting::DEFAULT_TRIAL_DAYS`); `Shop::TRIAL_DAYS` (14) remains only as the legacy baseline fallback. Extra seats: `plans.extra_seat_price_cents` ($9 on Shop and Pro, null on Solo = can't buy) and `shops.extra_seats`; `Shop::seatLimit()` = plan seats + extras (or the admin override), and `seatCapacity()` is what's enforced (trial shops get the top plan's seats). Enforced at invite (`SendShopInvitation`, pending invites hold a seat) and at accept; bought via `ShopSeatController` (owner-only, needs a live billing period, can't go below people already seated). Reducing seats is immediate, no refund. `PlanAdvisor` ignores seats.

## AI assistant (bring-your-own-key)

`Feature::AiAssist` (`ai-assist`) is a Start-up-and-above feature (`PlanSeeder`, plus a migration for existing databases) - trial gets it via `Shop::hasFeature()`, so when a trial ends on Free it simply stops, with no separate expiry logic, and resumes the moment the shop is on Start-up. `isShipped()` is true now that quote intake exists - if every AI feature is ever switched off again, flip it back, or the marketing page overclaims.

Each shop brings its own provider key at `/shop/ai` (Owner-only, `manage-shop`, never delegable - it spends money and decides where customer text is sent). `ShopAiSetting` (`shop_ai_settings`, `BelongsToShop`) holds provider + model + the key; the key is an `encrypted` cast, `$hidden`, **write-only** (the page only ever gets `keyHint()`), and `api_key` is in `dontFlash` in `bootstrap/app.php` so a failed form can't flash it into the session. Provider and model come from the curated list in `config/ai.php`, never free text, and base URLs are fixed - no shop-supplied endpoint, so the key field can't become a request to an arbitrary host. Saving makes a real test call first (`AiManager::test()`); a rejected key is never stored. The OpenAI model names in `config/ai.php` are conservative placeholders - confirm them against OpenAI's current list before launch.

Code lives in `App\Services\Ai\`: `TextModel` (the main LLM; `AnthropicTextModel`/`OpenAiTextModel`, built on the `Http` facade like `QuickBooksClient` so tests use `Http::fake()`), `AiManager` (the one way to get a model - takes the `Shop` explicitly so queued work, which has no auth user, resolves the same as a request, and re-checks `hasFeature()` every call so a job queued before a trial ended stops when it ends), and `AiException` (messages are always safe to show - never the key or the provider's raw response). `DecisionModel` is an **unused interface**, the seam for a System 1 decision model (Jev/Clef/Tev1) as a later token-saving supplement to the main LLM - see the plan in `~/.claude/plans/`. `EnsureFeatureEnabled` lets *safe* requests through for any shop that ever trialed, so the AI settings page stays viewable (and says "paused") after a lapse while saving is refused; any AI endpoint or MCP route that must stop outright needs strict `hasFeature()`, not just the `feature:` middleware on a GET.

**Quote intake** (the first AI feature): the quote form's "Draft from a customer email" panel (`AiQuoteDraftPanel.tsx`) posts the pasted text to `QuoteAiDraftController` (`POST quotes/ai-draft`, strict `feature:ai-assist` + `quotes.create`; returns plain JSON, saves nothing). `App\Services\Ai\QuoteDrafter` sends the model only id + name (+ material type / what a tool cuts) for the shop's own catalog - never costs - with the customer's text fenced in `<customer_message>` and described to the model as untrusted data. The model only *chooses* (type, quantity, which catalog item); **cost and markup are filled client-side from the catalog** by `lineItemFromSuggestion()` (`resources/js/lib/aiQuoteDraft.ts`), mirroring what `QuoteLineItemCard` does when a person picks the item (cheapest supplier price, equipment rate, tool cost), so a model can never put a number on a quote. Every id it returns is checked against the list that was sent for that line type, and anything else (hallucinated, another shop's, wrong list) is dropped to "no match". Suggested lines are flagged with a client-only `ai_note` ("AI: check" badge) until the owner edits them. A message over `config('ai.max_message_length')` is rejected rather than truncated, and a catalog over `ai.max_catalog_items` per list tells the owner the draft only saw part of it.

`ai_requests` (`AiRequest`, `BelongsToShop`) logs every AI call - feature, provider, model, tokens, latency, ok/error - and deliberately **never the prompt or the answer** (customer data). It is written with an explicit `shop_id`, since the service can run without an auth user.

**Stale-quote follow-up**: a "Draft follow-up" link on each stale-quote row of the dashboard's attention list opens `FollowUpDraftDialog.tsx`, which posts to `QuoteFollowUpController` (`POST quotes/{quote}/ai-follow-up`, strict `feature:ai-assist` + `quotes.view`, sent and open quotes only). `QuoteFollowUpDrafter` drafts a subject and body; it **never sends** - the owner edits it, then copies it or opens it in their own mail app (`mailto:`). The model sees the shop, sender, customer name, send date, due date and what was quoted - **not** quote notes or customer notes (they can hold things never meant for the customer), not the customer's email, and the total only for someone with `financials.view`. Both AI features log through `AiUsage::record()`.

### MCP server (the shop's own AI reads the shop)

`routes/ai.php` registers one endpoint, `POST /mcp` (`App\\Mcp\\Servers\\ShopServer`, package `laravel/mcp`), behind `auth:sanctum` → `mcp.agent` (`AuthenticateMcpAgent`) → `throttle:mcp`. **Read-only by default, with opt-in writes per resource.** `ShopServer::TOOLS` is the single list of tools; which of them a connection sees is decided per request (`McpTool::shouldRegister()` = the agent holds that tool's permission), and `get-access` reads the same list to report it. `defaultPaginationLength` is raised to 50 on purpose - the default (15) splits the tool list across pages and a client that doesn't follow the cursor would silently never see the rest.

**What can be granted is a hard ceiling, `App\\Support\\AgentAccess::grantable()`**: per resource, any of `view` / `create` / `update` (customers, quotes, materials, services, equipment, tooling, business partners: all three; jobs: view + update; job stages and financials: view only). There is no `delete` anywhere, no job create/cancel, nothing for the team, roles, shop settings, billing, add-ons, markup defaults, QuickBooks, procedures or certifications - `overridesFor()` drops anything not on the list, and a write permission always brings its `view` along. Adding a tool = add the permission to `grantable()` and a tool that checks it; a grant with no tool behind it would be a switch that does nothing.

Write tools (`CreateCustomerTool`, `UpdateQuoteTool`, `MoveJobTool`, `Catalog/*` ...) each validate with the same rules as the matching web form, reject ids from other shops (`Rule::exists(...)->where('shop_id', ...)` / scoped finds), write an `activity('mcp')` entry with the agent as causer via `McpTool::audit()`, and carry `#[IsReadOnly(false)] #[IsDestructive(false)]`. Rules that exist for safety and should not be loosened without thought: quotes created are always `Draft`, and `update-quote` only edits a *draft* that is not archived and has not become a job (it can't send, mark won/lost, archive or convert); `move-job` goes through `App\\Actions\\MoveJobToStage` (shared with the job board, so period dates, history, broadcast and the QuickBooks hook can't drift) but refuses the Shipped and Invoiced stages and cancelled jobs; `update-job` assigns by member *name* (humans only, never an agent) and refuses cancelled jobs; `create-*` tools refuse a case-insensitively same-named record unless `allow_duplicate`. Quote line costs are never typed by the AI by default: `Mcp\\Support\\QuoteLineResolver` fills cost and markup from the catalog exactly as the quote builder does when a person picks an item (cheapest supplier price, equipment rate, tool cost, employee hourly rate, shop default markup); an explicit `unit_cost`/`markup_percent` is accepted as an override, like typing over the field, and a line with no link and no cost starts at $0. Supplier prices live on the **business partner** (its materials/services lists), not on materials or services, so that's where the AI sets them; on `update-business-partner` a list is only replaced if it is sent.

**The AI is told what it can do.** `get-access` (always available, "START HERE") returns the shop, a plain summary ("You can look at ... / You can create or change ..."), per resource what it `can` do and what the owner `could_be_granted`, `tools_you_have` (with `writes` true/false), `never_allowed`, the rules the tools follow, and `sees_money`. The server `#[Instructions]` tell the client to call it first. A tool that is missing from the list is not available.

**The identity is a per-shop agent user, never a token on a person.** Everything tenant-scoped keys off `users.current_shop_id`, which a human can switch from the shop menu - a token minted for a person would silently follow them into another shop. `CreateShopAgent` makes a `User` with `is_agent = true` (not fillable; set via `forceFill`) that belongs to exactly one shop, has no password anyone knows, an email on `@agents.invalid`, and **no Spatie role**: its access is only `{resource}.view` grants stored as `permission_overrides` on its `shop_user` row, which `User::shopPermissions()` already resolves (`App\Support\AgentAccess` is the allow-list of what can be granted - view only, financials and suppliers opt-in). Consequences to remember: `Shop::members()` **excludes agents** (`where users.is_agent = false`) so they take no seat and never appear in the Team page, employee or assignee pickers - use `Shop::agents()` to reach them; the login form refuses them (`is_agent => false` in `LoginRequest`); `config/sanctum.php` has `guard => []` so a browser session cookie can never authenticate `/mcp` (the default `['web']` would let a logged-in human in as themselves).

`AuthenticateMcpAgent` requires `is_agent`, a token with the `mcp` ability, a non-suspended shop and a strict `hasFeature(AiAssist)` - when AI access lapses the endpoint stops outright and the tokens simply work again on resubscribing. It also sets Spatie's permissions team id, which the `web` middleware group normally does and this route doesn't run. `McpTool` (base class) enforces each tool's permission itself, hides tools the agent can't use (`shouldRegister`), turns any failure into a readable error, and writes `mcp_requests` (tool, status, timing - never arguments or results). Attributes aren't inherited in PHP, so each concrete tool carries its own `#[Name]`, `#[IsReadOnly]`, `#[IsIdempotent]`. Money (quote totals, unit costs, job price) is returned only if the agent holds `financials.view`, same rule as the dashboard - write responses too. A test or script that makes more fixtures *after* a tool call must call `app('auth')->forgetGuards()` first (the test stays logged in as the agent, so the tenant scope hides other shops' rows from factories).

The owner manages it at `/shop/ai` (`ShopAiAgentController`, `McpConnectionPanel.tsx`; owner-only): turn on, choose what it can see and - in a collapsible roles-and-permissions-style matrix - what it can create and update (the form posts `permissions`, an array of `resource.action`), create a token (name + days, default `config('ai.mcp_token_days')`, never "no expiry"), revoke, turn off (deletes the agent and every token). A token's plaintext exists only as a one-time session flash (`new_token`) on the redirect after creating it - Sanctum stores a hash. Not built: OAuth (claude.ai and ChatGPT one-click connectors need it; bearer tokens work for Claude Desktop/Code and custom clients - `Mcp::oauthRoutes()` plus Passport is the documented route), a UI for the `mcp_requests` log, an undo for AI changes beyond the history entries, and an "accepted or not" signal on `ai_requests`.

Not built yet: CSV column mapping, the hosted-AI add-on, and the System 1 decision-model supplement (`DecisionModel` is still an unused interface).
