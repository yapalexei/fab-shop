# Legal pages and consent records

Public pages `/terms`, `/privacy` and `/sms-terms` (`LegalController`, `Pages/Legal/*`) - linked from the marketing page footer, `GuestLayout` (login/register), the invitation page, onboarding, the in-app footer (`AuthenticatedLayout`) and the shared mail footer (`resources/views/vendor/mail`). Who the documents are *from* (company name/address/contact, governing law) comes from `config/legal.php` via `LEGAL_*` env vars; unset values render as bracketed placeholders, so nothing placeholder-ish ships unnoticed. The wording is a drafted starting point, not legal advice - have counsel review it before launch.

`consent_records` is an **append-only** audit trail (`ConsentRecord` throws on update/delete; withdrawing = a new `granted = false` row): who (user/shop FKs are `nullOnDelete`, with `subject_email`/`subject_phone` kept), which `ConsentType` (terms / privacy / sms), the document `version` (from `config/legal.php` - bump it whenever the document or checkbox wording changes), the *exact wording shown*, source, IP and user agent. It is deliberately not `BelongsToShop` (registration happens before a shop exists and no tenant should read it) and has no UI. Record through `App\Support\Consent`, which also owns the checkbox strings (`AGREEMENT`, `smsOptInText()`) - the frontend is given those strings, never retypes them, so the stored text can't drift from what was on screen.

Registration and invitation-accept (new account) require the `accepted_terms` checkbox (`TermsAgreement`) and call `Consent::recordAgreement()`. SMS is **prepared, not live**: `SmsConsentCheckbox` + `Consent::recordSms()/hasSmsConsent()` exist for whichever form first collects a mobile number (must be its own unchecked, optional checkbox - never bundled with the Terms, never a condition of purchase), and the SMS Terms/Privacy pages carry the A2P 10DLC language (program, frequency, rates, STOP/HELP, no sharing of mobile opt-in data). Users who registered before this existed have no recorded acceptance; a re-acceptance gate on version bumps is not built.

**Agreeing again when subscribing.** Registration and invitation-accept aren't the only places the Terms are accepted: anything that commits a shop to paying - changing plan (`ShopPlanController::update`), subscribing to an add-on, buying extra seats (not giving them back) - calls `Consent::requireAgreementToSubscribe()`. If the person's latest Terms consent isn't a grant for the *current* `legal.versions.terms` (`Consent::hasAcceptedCurrentTerms()`), the request must carry the ticked `accepted_terms` box or it's refused with a validation error; the agreement is then recorded on the spot (`source = 'subscription'`, same wording as registration). So **bumping the Terms version means every owner is asked again at their next purchase**, and only then - a global "accept the new Terms before you can use the app" gate for existing users is still not built. The confirmation dialogs (`SubscriptionTerms.tsx`, props `terms.accepted` / `terms.text` from `Consent::subscriptionTerms()`) always link the Terms and show the box only when it's needed; the server rule is the guarantee. In tests `actingAsShopMember()` records agreement by default (`agreedToTerms: false` to test the gate).

**Price-change wording (Terms section 4).** Decreases apply immediately; increases that apply to existing subscriptions take effect on an effective date announced at least `shop.price_increase_notice_days` (15) ahead by email and in the app, apply to the first payment on or after that date, and can be avoided by cancelling first; we may choose not to apply an increase to existing subscriptions; features are added freely, never removed by a price/plan change, and a discontinued feature stops being billed. The wording is a drafted starting point - have counsel review it - and the behavior in `plans-and-pricing.md` must keep matching it (including the notice days, which come from the same config value as the admin form's default).
