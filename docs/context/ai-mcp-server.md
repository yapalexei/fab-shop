# MCP server (the shop's own AI reads the shop)

`routes/ai.php` registers one endpoint, `POST /mcp` (`App\\Mcp\\Servers\\ShopServer`, package `laravel/mcp`), behind `auth:sanctum` → `mcp.agent` (`AuthenticateMcpAgent`) → `throttle:mcp`. **Read-only by default, with opt-in writes per resource.** `ShopServer::TOOLS` is the single list of tools; which of them a connection sees is decided per request (`McpTool::shouldRegister()` = the agent holds that tool's permission), and `get-access` reads the same list to report it. `defaultPaginationLength` is raised to 50 on purpose - the default (15) splits the tool list across pages and a client that doesn't follow the cursor would silently never see the rest.

**What can be granted is a hard ceiling, `App\\Support\\AgentAccess::grantable()`**: per resource, any of `view` / `create` / `update` (customers, quotes, materials, services, equipment, tooling, business partners: all three; jobs: view + update; job stages and financials: view only). There is no `delete` anywhere, no job create/cancel, nothing for the team, roles, shop settings, billing, add-ons, markup defaults, QuickBooks, procedures or certifications - `overridesFor()` drops anything not on the list, and a write permission always brings its `view` along. Adding a tool = add the permission to `grantable()` and a tool that checks it; a grant with no tool behind it would be a switch that does nothing.

Write tools (`CreateCustomerTool`, `UpdateQuoteTool`, `MoveJobTool`, `Catalog/*` ...) each validate with the same rules as the matching web form, reject ids from other shops (`Rule::exists(...)->where('shop_id', ...)` / scoped finds), write an `activity('mcp')` entry with the agent as causer via `McpTool::audit()`, and carry `#[IsReadOnly(false)] #[IsDestructive(false)]`. Rules that exist for safety and should not be loosened without thought: quotes created are always `Draft`, and `update-quote` only edits a *draft* that is not archived and has not become a job (it can't send, mark won/lost, archive or convert); `move-job` goes through `App\\Actions\\MoveJobToStage` (shared with the job board, so period dates, history, broadcast and the QuickBooks hook can't drift) and follows the board's own rules (`Job::canTransitionTo`); it was deliberately opened up to every stage including Shipped and Invoiced, but it still refuses cancelled jobs - see the Invoiced note under "Prompt injection" below; `update-job` assigns by member *name* (humans only, never an agent) and refuses cancelled jobs; `create-*` tools refuse a case-insensitively same-named record unless `allow_duplicate`. Quote line costs are never typed by the AI by default: `Mcp\\Support\\QuoteLineResolver` fills cost and markup from the catalog exactly as the quote builder does when a person picks an item (cheapest supplier price, equipment rate, tool cost, employee hourly rate, shop default markup); an explicit `unit_cost`/`markup_percent` is accepted as an override, like typing over the field, and a line with no link and no cost starts at $0. Supplier prices live on the **business partner** (its materials/services lists), not on materials or services, so that's where the AI sets them; on `update-business-partner` a list is only replaced if it is sent.

**The AI is told what it can do.** `get-access` (always available, "START HERE") returns the shop, a plain summary ("You can look at ... / You can create or change ..."), per resource what it `can` do and what the owner `could_be_granted`, `tools_you_have` (with `writes` true/false), `never_allowed`, the rules the tools follow, and `sees_money`. The server `#[Instructions]` tell the client to call it first. A tool that is missing from the list is not available.

**The identity is a per-shop agent user, never a token on a person.** Everything tenant-scoped keys off `users.current_shop_id`, which a human can switch from the shop menu - a token minted for a person would silently follow them into another shop. `CreateShopAgent` makes a `User` with `is_agent = true` (not fillable; set via `forceFill`) that belongs to exactly one shop, has no password anyone knows, an email on `@agents.invalid`, and **no Spatie role**: its access is only `{resource}.view` grants stored as `permission_overrides` on its `shop_user` row, which `User::shopPermissions()` already resolves (`App\Support\AgentAccess` is the allow-list of what can be granted - view only, financials and suppliers opt-in). Consequences to remember: `Shop::members()` **excludes agents** (`where users.is_agent = false`) so they take no seat and never appear in the Team page, employee or assignee pickers - use `Shop::agents()` to reach them; the login form refuses them (`is_agent => false` in `LoginRequest`); `config/sanctum.php` has `guard => []` so a browser session cookie can never authenticate `/mcp` (the default `['web']` would let a logged-in human in as themselves).

`AuthenticateMcpAgent` requires `is_agent`, a token with the `mcp` ability, a non-suspended shop and a strict `hasFeature(AiAssist)` - when AI access lapses the endpoint stops outright and the tokens simply work again on resubscribing. It also sets Spatie's permissions team id, which the `web` middleware group normally does and this route doesn't run. `McpTool` (base class) enforces each tool's permission itself, hides tools the agent can't use (`shouldRegister`), turns any failure into a readable error, and writes `mcp_requests` (tool, status, timing - never arguments or results). Attributes aren't inherited in PHP, so each concrete tool carries its own `#[Name]`, `#[IsReadOnly]`, `#[IsIdempotent]`. Money (quote totals, unit costs, job price) is returned only if the agent holds `financials.view`, same rule as the dashboard - write responses too. A test or script that makes more fixtures *after* a tool call must call `app('auth')->forgetGuards()` first (the test stays logged in as the agent, so the tenant scope hides other shops' rows from factories).
