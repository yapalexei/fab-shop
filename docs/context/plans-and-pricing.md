# Plans and pricing

Launch prices (hypotheses, not market-validated), seeded by `PlanSeeder` (after launch a platform admin owns them - see "Tier management" below; re-running the seeder only rewrites each tier's *current* version): Solo $29 (1 seat), Shop $59 (4 seats; the plan's key is still `start-up`, only its display name changed), Pro $119 (10 seats). Job board, quote history and AI quote drafting start at Shop; material tracking, qualification records and `Feature::AiAgent` (MCP access) are Pro, with the first two also sold as $25 add-ons. The default trial is 30 days (`PlatformSetting::DEFAULT_TRIAL_DAYS`); `Shop::TRIAL_DAYS` (14) remains only as the legacy baseline fallback. Extra seats: `plans.extra_seat_price_cents` ($9 on Shop and Pro, null on Solo = can't buy) and `shops.extra_seats`; `Shop::seatLimit()` = plan seats + extras (or the admin override), and `seatCapacity()` is what's enforced (trial shops get the top plan's seats). Enforced at invite (`SendShopInvitation`, pending invites hold a seat) and at accept; bought via `ShopSeatController` (owner-only, needs a live billing period, can't go below people already seated). Reducing seats is immediate, no refund. `PlanAdvisor` ignores seats.

## Tier management (platform admin: versions, expiry, history)

A platform admin adds, edits and retires tiers at Platform admin > Plan tiers (`PlanSettingController`, `PlatformAdmin/Plans.tsx`, `can:platform-admin` only - nothing here is reachable from a shop's pages). Tiers are **never edited in place or deleted**, because shops may still be on them:

- **A `plans` row is one *version* of a tier.** `key` names the tier and is shared by every version; `version` counts up; `superseded_at` is set on a version when a newer one replaces it. `(key, version)` is unique and a partial unique index allows exactly one current (not superseded) row per key. A shop's `plan_id` points at the exact version it signed up for, so `$shop->plan->monthly_price_cents`, `->user_limit`, `->features()` and `extra_seat_price_cents` keep returning what it bought - `Billing`, `seatLimit()`, `hasFeature()` and the revenue summary needed no change.
- **`Plan::applyEdit()`**: if the name, price, seats, extra-seat price or feature list changed (`Plan::VERSIONED` + features), it archives the current row and publishes a new version (copying `stripe_price_id`); otherwise it updates `position` / `expires_on` / `show_expiry` in place. Archived versions can't be edited (`PlanSettingController::ensureEditable()`). Right after a new version is published, `App\Actions\PropagateTierChange` decides what the shops on older versions of the tier get (next bullet).
- **What existing shops get when a tier changes** (`PropagateTierChange`, run when a version is published and again, idempotently, by the hourly `app:apply-scheduled-plan-changes`; the admin's flash message reports the counts):
  - **Features: they keep everything they have and gain whatever is added**, immediately, whichever way the price went. A feature the new version drops stays with them. Because plan rows are immutable, the difference lives on the shop: `shops.extra_features` (`Shop::extraFeatures()`; `planFeatures()` = the row's features + extras, `hasPlanFeature()`). **Anything asking "what does this shop's plan include" must use `$shop->planFeatures()` / `hasPlanFeature()` / `hasFeature()`, never `$shop->plan->features()` / `->hasFeature()`** - that would ignore the carried-over features.
  - **A LOWER price applies to every shop on the tier the moment it is saved** - no waiting for a paid period, nothing for the owner to do, no "moving plans" (`Shop::moveToPlan()`). They're emailed that it's in effect; amounts already paid aren't adjusted (there is no payment processor yet, so "applies" means their plan row now carries the lower price and their next payment is at it).
  - **A HIGHER price is the admin's choice, per published version**: `plans.apply_to_subscribers` (default false = grandfathered: shops keep the price they signed up for and nobody is emailed) and `plans.subscribers_effective_on`. With the box on, a date ahead sets `shops.pending_plan_id` + `pending_plan_effective_at` (midnight starting that day in the *shop's* timezone), emails the owner **now** with the date and their right to cancel first, and `app:apply-scheduled-plan-changes` moves the shop when the date arrives; a null/past date moves everyone immediately (the admin form warns that this skips the notice). The form proposes today + `shop.price_increase_notice_days` (15) - the same number the Terms promise (section 4, "Price changes"; `LegalController` passes it to the page). The date can't be in the past (`SavePlanRequest`). Publishing again replaces a pending increase (and re-notifies); a version at the shop's current price calls it off; a lower one clears it by moving the shop.
  - A shop is left on its earlier version (counted in the admin's message) when moving would shrink its seats, or make its bought extra seats dearer. **The Free tier never moves anyone on price** - it's where lapsed trials land, not something anyone subscribed to.
  - `Shop::moveToPlan()` keeps every feature (carrying over what the new row lacks) and cancels add-ons the new row now bundles. A shop (or admin) picking a different plan by hand clears the pending move, `extra_features` and the notice (the `Shop::saving` hook; `moveToPlan()` opts out).
  - The hourly command also **catches up** shops left on an older version (published before this rule existed, or placed there by hand): it re-runs the propagation for every tier's current version.
- **What is offered**: `Plan::scopeOffered()` = current version AND (`expires_on` null OR `expires_on` > today). **Everything that lets a person pick a plan goes through `Plan::orderedByTier()` / `Plan::offeredByKey()`** (marketing page, onboarding, the shop Plan page, `PlanAdvisor`, the trial seat cap). Never look a plan up by `where('key', ...)` for a *new* assignment - that can return an archived version; use `Plan::current()` / `offeredByKey()`. `expires_on` is the date the tier leaves the list (exclusive); `show_expiry` decides whether the marketing/onboarding/Plan pages print "Available until ..." (otherwise it just disappears). "Remove from public list" sets `expires_on` to today.
- **Order is the `position` column**, not the old hardcoded key list (`Plan::DEFAULT_ORDER` is now only the factory/seeder default). "Higher tier" comparisons (upgrade-only on the Plan page, `Shop::canUpgrade()`) use `Plan::rank()` - the tier's *current* position - so a shop on an archived version still compares correctly. Ties are not an upgrade.
- **The Free tier (`Plan::FALLBACK_KEY`)** is where a shop lands when its trial ends: editable (and versioned) like the others, but it can't be given an expiry or retired.
- **A shop on an archived version or a retired tier** keeps working and can switch its own plan to annual billing at its own price; the Plan page shows a notice (the `currentPlan` prop is the plan it is actually on, with its carried-over features, separate from the offered `plans` list; `pendingChange` is a promised lower price) and it can only move to a *higher* tier. It cannot "move" to the newer version of its own tier by hand - a lower price arrives on its own as above, a higher one deliberately doesn't.
- **The page** (`PlatformAdmin/Plans.tsx`) draws each tier as a card like the landing page's (4-column CSS grid at `lg`), with a pencil (opens the edit dialog) and an archive icon (confirmation dialog, then `plans.retire`; hidden for Free), plus a dashed "+" tile that opens the same dialog empty. "Archive" = sets `expires_on` to today; clearing the date in the edit dialog brings it back.
- **History** (at the bottom of a tier's edit dialog): every archived version with its values, the dates it was in effect and how many shops are still on it (`shops.plan_id` count, trial and Free shops included). The shop directory's plan filter / override dropdown lists archived and removed versions that still have shops, labelled.
- Create/change/remove each write a `platform admin: plan tier ...` entry to the security log (no shop id - it's platform-wide).

### Telling shops what changed (before/after)

Whenever a tier change gives a shop something, its owner gets one email (`PlanUpdated`) and a summary on the Plan page, as a diff of what they had vs. what they have now, not a bare "your plan changed": the **features now included on top of what they had** (label + tagline), the **price** (old -> new per their billing interval, and the date it starts), any **seats** change, and - rarely - **features that are gone**. `Shop::announcePlanChange($changes)` is the only way to do this: it merges into `shops.plan_notice` (shown on the Plan page until the owner clicks "Got it", `shop.plan.notice.dismiss`, owner-only; cleared when the shop picks a different plan) and sends the email, which carries only that one change. Nothing is announced when nothing changes for the shop (a higher list price that doesn't reach them, a tier edit that adds nothing).

### A feature discontinued for good

Rare: a feature we can no longer support (the example: AI). It is a decision made in code - add its value to `shop.discontinued_features` in `config/shop.php` and deploy (`Feature::isDiscontinued()`). From then on `Shop::hasFeature()` / `planFeatures()` / `enabledFeatures()` say no for every shop however it got the feature (plan row of any version, carried-over `extra_features`, add-on, trial), `isShipped()` is false (so it leaves the marketing page and the add-ons list, and add-on purchase 404s), and the tier editor shows it as Discontinued and drops it from a saved tier. The daily `app:announce-discontinued-features` then, for each shop that had it: cancels the add-on (nothing keeps billing), removes it from `extra_features`, emails the owner ("no longer available - removed from every plan - any add-on cancelled, you won't be billed") and records it in `shops.notified_discontinued_features` so it runs once. This is different from *removing a feature from one tier*, which existing shops keep.

## Comparison table and cost calculator

Both read the live plan data, so a tier edit shows up in them at once (nothing is hardcoded).

- **Landing page** (`Welcome.tsx`, under the tier cards): `PlanComparisonTable` - one column per offered tier, rows for monthly and yearly price (monthly x `annualMonthsCharged`), people included, extra-person price, then a tick for each shipped feature the tier includes. The Free column is the trial: "Free for N days", every feature ticked, seats of the biggest plan (what `Shop::seatCapacity()` gives a trial).
- **Upgrade page** (`ShopPlan/Index.tsx`): the same table inside `PlanCostCalculator`. The owner sets how many people and ticks the features they need (starting from what the shop uses today: `planFeatures()` + active add-ons, deliberately not the trial's unlock-everything), and every plan is priced for that - plan, extra people, add-ons for needed features the plan lacks - monthly and yearly, lowest marked, plan that can't seat that many people flagged. This includes Free plus add-ons, which is a real way to subscribe. A shop on an earlier version or a removed tier sees its own plan as an extra column at its own price. The Upgrade buttons under each column use the same confirmation flow as the cards.
- The arithmetic is `resources/js/lib/planCost.ts` (pure; an annual bill is the monthly figure x months charged, matching `Billing::periodPriceCents()`). There is no JS test runner, so the tests cover the *data* it is fed (`tests/Feature/PlanComparisonDataTest.php`): extra-seat prices, ticked feature keys, live add-on prices, the starting selection, earlier versions, discontinued features. If `Billing`'s pricing rules change (e.g. proration), update `planCost.ts` with them. Quotes shown when actually confirming a change still come from `Billing::planChangeQuote()`, not from this table.
