# Self-hosted edition (`APP_MODE=selfhosted`)

One codebase, two editions. The cloud edition is the multi-tenant service we run; the self-hosted edition is a single shop's own copy. **It is the same code and the same schema** - a self-hosted install is simply one tenant, so `shop_id`, `BelongsToShop` and the permission model are untouched. What the mode removes is everything that only exists because *we* run the service for many shops: plans, trials, seat limits, add-ons, the platform admin console, public sign-up, the marketing page and our legal pages. This was chosen over a second repo (every fix would have to land twice) and over stripping out tenancy (a huge refactor that buys nothing). Whether anyone will pay for a self-hosted edition is **not validated** - this is the cheap spike that tests the technical cost, not a launched product.

`App\Support\Edition` is the only switch: `Edition::selfHosted()` / `cloud()` read `config('app.mode')` (`APP_MODE`). `APP_MODE` is shared with `demo`, so the two are mutually exclusive.

## What changes

| Area | Self-hosted behaviour | Where |
|---|---|---|
| Entitlements | `Shop::hasFeature()` is true for every shipped, non-discontinued feature; `enabledFeatures()` lists them; `readOnlyFeatures()` empty; `canUpgrade()` false; `seatLimit()`/`seatCapacity()` null (unlimited). No plan row or trial is needed - the installer leaves `plan_id` and trial dates null. | `Shop.php` |
| Cloud-only routes | 404 via the `cloud` middleware: `/terms`, `/privacy`, `/sms-terms`, `/register`, `/platform-admin/*`, `/shop/plan`, `/shop/seats`, `/shop/addons*`, shop-deletion request/cancel, trial-ended dismiss. **The routes stay registered** (the Ziggy route table the frontend builds links from is identical in both editions); the pages are just gone. A signed-out visitor to a cloud-only auth route still gets the login redirect first (auth runs before `cloud` in middleware priority) - harmless. | `routes/web.php`, `routes/auth.php`, `CloudOnly` |
| `/` | Redirects to `/setup` until installed, then to `/dashboard` (which sends signed-out visitors to sign in). `/login` also goes to `/setup` while nobody exists. | `MarketingController`, `AuthenticatedSessionController` |
| First run | `/setup` (`SelfHostedOnly` + `guest`, 404 in cloud) or `php artisan selfhosted:install`. Both call `InstallSelfHostedShop`: owner account (email pre-verified - mail may not be configured yet), the shop, `seedRoles()`, Owner role, and the shop is left at onboarding step `team` so the owner gets the same short wizard cloud signups do. **Closes permanently once any user exists** (`Edition::installed()`), checked before validation; a Postgres advisory lock stops two simultaneous requests both becoming owner. Logged as `self-hosted install completed`. | `SelfHostedSetupController`, `SelfHostedInstall`, `Setup/Index.tsx` |
| Scheduler | `app:notify-expired-trials`, `app:purge-deleted-shops`, `app:apply-scheduled-plan-changes`, `app:announce-discontinued-features` are skipped via `->when(Edition::cloud())`. (`schedule:list` still shows them - the filter runs at fire time.) Data-export pruning still runs. | `routes/console.php` |
| SEO | `robots.txt` is `Disallow: /` regardless of `APP_ENV`. | `Seo::robotsTxt()` |
| Frontend | Shared Inertia prop `selfHosted`. `LegalLinks` renders nothing; the Add-ons nav item and the "Delete this shop" card are hidden. Everything plan/trial-shaped (`TrialBanner`, Upgrade button, plan name) is driven by props that are already null/false. Data **export** is kept (portability is a selling point); data **deletion** is cloud-only (you own the server). | `HandleInertiaRequests`, `LegalLinks.tsx`, `AuthenticatedLayout.tsx`, `OwnerSecurityControls.tsx` |

Invitations, the team page, roles/permissions, per-member overrides, 2FA policy, the security log, CSV import, AI (bring-your-own-key) and the MCP endpoint all work unchanged.

## Rules for new code

- **A new feature must be gated through `Shop::hasFeature()`**, never by testing a plan or trial directly - that is what makes it work in both editions for free.
- **Anything about plans, billing, trials, seats-for-sale, our legal terms, or cross-tenant admin gets the `cloud` middleware** (and its UI hidden on `selfHosted`). A new cloud-only scheduled command gets `->when(fn () => Edition::cloud())`.
- Don't branch on `Edition` deep in business logic; keep it at the edges (entitlements, routes, scheduler, shared props). If you find yourself adding a third place, add a method to `Edition` or `Shop` instead.
- Cloud-edition tests must keep passing with `APP_MODE` unset; self-hosted tests set `config(['app.mode' => Edition::SELF_HOSTED])` (`tests/Feature/SelfHostedModeTest.php`).

## Trying it locally (without Docker)

`APP_MODE=selfhosted` against an **empty** database (the install refuses if any user exists, so don't point it at dev data - use a scratch database). `php artisan serve` forwards only a whitelist of env vars to its child process, so env overrides are silently ignored; use `.env`, or PHP's built-in server (`cd public && php -S ... ../vendor/laravel/framework/src/Illuminate/Foundation/resources/server.php`) which inherits the environment. `npm run build` runs on the host (macOS native binaries), and the feature tests need a built manifest for any new Inertia page.

## The Docker bundle (`docker/selfhosted/`)

The customer-facing stack - not `compose.yaml` in the repo root, which is the Sail *dev* stack. Details for customers are in its [README](../../docker/selfhosted/README.md); what matters when changing code:

- **One image, four containers** (web, horizon, scheduler, reverb) built from the root `Dockerfile`, plus Postgres, Redis and **Caddy**, the only published service. `./install.sh` writes `.env` (fresh `APP_KEY`, DB password, Reverb keys and a **setup key**), builds and starts, and prints `/setup?key=...`. It keeps an existing `.env` so secrets never change on a re-run. `backup.sh`/`restore.sh` cover the database, the shared files volume and `.env` (the `APP_KEY` is needed to read encrypted data).
- **Migrations run on `web` start** (`AUTORUN_ENABLED`, serversideup image) and the other three containers wait on web's healthcheck (`/up`), so "healthy" means "schema is current". This avoids the cloud's "reverb starts before migrations" crash.
- **Files:** `FILESYSTEM_DISK=local` with one named volume mounted at `storage/app` in all four app containers (the cloud uses a bucket). Code must still go through the default/media disk, never `Storage::disk('local')->path()`.
- **Reverb is same-origin.** Caddy sends `/app/*` to Reverb and everything else to web; `/apps/*` (the app pushing events) is deliberately not proxied. Nothing about the hostname is baked into the image: `resources/js/echo.ts` uses `VITE_REVERB_*` when the build has them (cloud, Sail) and otherwise `window.location`; the public app key is read from a `<meta name="reverb-key">` the root view renders, not from the bundle. The CSP (`SecurityHeaders`) adds `ws(s)://<this host>` to `connect-src` when self-hosted and no Reverb host is configured. The root `Dockerfile` therefore no longer defaults `VITE_REVERB_PORT/SCHEME` - an empty value means "same origin".
- **`/setup` is protected by `SELFHOSTED_SETUP_KEY`** when set (404 without `?key=`), because an install exposed to the internet is first-come-first-served until the owner exists. The CLI command is unaffected (it implies shell access). Unset = open (local installs, tests).
- **`.dockerignore` keeps a working copy's local files out of the image.** It excludes `docker/` (`docker/selfhosted/.env` holds secrets, and a plain `.env` pattern only matches at the repo root) and `storage/app/{private,public}/*` - without it a build from a dev checkout copied hundreds of uploads and CSV imports into the image and, via the volume, into the customer's data (found when the first backup came out 5.5 MB). A build from `git clone` never had them; keep the rule anyway.
- **Build once.** Only `web` has a `build:` section; four services building one tag fail with "image already exists". The three other app containers disable the image's built-in healthcheck (it probes nginx, which they don't run).

## Not done yet (known gaps before this could be offered to anyone)

- **Operations.** `backup.sh`/`restore.sh` are a local-disk backup only (the README tells owners to copy `backups/` off the machine - nothing enforces it). A restore onto a freshly wiped install (database, uploaded file, sign-in as the restored owner) has been exercised once by hand, not in CI. Update = `git pull && docker compose up -d --build` on the customer's machine (no prebuilt registry image, so the first build compiles PHP extensions - minutes). Mail defaults to `MAIL_MAILER=log`, so invitations and resets are written to the container log until the owner configures SMTP; a "copy the invite link" fallback in the UI would remove that dependency.
- **Job photos are served from a public path** (`/storage/...`, `Media::getUrl()`) on a local disk, unlike the cloud's signed S3 URLs (`JobController::photoUrl()`). Guessable-ish, not access-checked. Fix before offering to anyone: serve them through a controller, or add MinIO. Other attachments already go through controllers.
- **Licensing and money.** No license key, no decision on the license (AGPL vs source-available vs commercial), nothing written about what we support. `shop_user`-level terms/consent for a self-hosted owner are intentionally not recorded.
- **Dead weight, not harm:** plan/feature/platform tables and seeders still migrate into a self-hosted database; `PlatformSetting`/`FeatureSetting` rows are simply never read. Migrations that insert plan rows assume the tables exist, so don't prune them without checking.
- **Verified by hand (headless Chromium against the real stack, not in CI):** install.sh end to end; `/setup` form (404 without the key, closes afterwards); sign-in; the onboarding wizard; the job board opening `ws://<site>/app/<key>` under the production CSP, subscribing to its private channel and refetching when the app broadcasts; backup then restore onto a wiped install. Not verified: https/Let's Encrypt (needs a public domain), `linux/amd64` builds (tested on arm64 only), an upgrade from an older version, a real SMTP server, phones/tablets on a LAN.
