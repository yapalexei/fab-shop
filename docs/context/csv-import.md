# CSV import (F9)

One mechanism shared by seven resources (Customers, Materials, Services, Business Partners, Equipment, Tooling, Material types) rather than one per resource - see `App\Support\CsvImport\`. `ResourceImporter` is the abstract shape each resource implements: its template columns, how a raw row resolves into model attributes (including name-based relational lookups - `material_type` on Materials, a `;`-separated `cuts` list on Tooling - resolved against the shop's own records, never auto-created), and the validation those attributes must pass. `ImporterRegistry` maps a route's `{resource}` key to one. Owner-only (`can:manage-shop`), gated per-resource by the same `Feature` each resource's own pages already require.

Processing is queued (`ProcessCsvImport`) - the upload endpoint returns the new `Import` row's id as plain JSON (not an Inertia redirect, since `CsvImportDialog.tsx` stays open on the current page rather than navigating), and the dialog polls `GET /imports/status/{import}` (also plain JSON) until status leaves `pending`. A row is matched to an existing record by case-insensitive `name` - matched, checkbox off, it's skipped; checkbox on, its fields are replaced. That dedupe check also looks at what the *same import run* has already created/updated (not just the database), so two rows in one file with the same name, however they differ in case, resolve as one record. A file whose headers already match the template imports as before (a missing column fails the whole file before any row is touched); any other file goes through a **column-mapping step** - `POST imports/{resource}/preview` returns the headers, sample rows and a guessed mapping (`ColumnMapper`, with a few supplier-export synonyms), the dialog lets the owner fix it, and the upload is re-sent with `mapping[column]` = zero-based file column (blank = leave empty). Each importer's `requiredColumns()` (default just `name`) must be mapped, and a file matching by name only needs those - other template columns may be absent (read as blank); nothing is stored between the two requests. **Supplier price lists** (`SupplierPriceImporter`, key `supplier-prices`, implements `ImportsOwnRows` so it bypasses the name-matching loop) are imported from a business partner's edit page, which sends `business_partner_id` (must be one of the shop's): rows are material + size + price (+ unit, part number, link), materials are matched by name and created if missing, price rows by material + size; an added or overwritten price counts as freshly checked, one already on file is skipped unless overwrite is on. The tooling template also carries `part_number`/`source_url`. Also: one bad row among valid ones is reported by row number while the rest still import.

Console/queue context has no authenticated user, so - like the demo commands and `NotifyExpiredTrials` - every query inside `ProcessCsvImport` filters by shop_id explicitly; the tenant global scope is a no-op there. Watch for the same silent-mass-assignment trap `Invitation::accepted_at` hit: `Import`'s count/error columns must be in its `$fillable` list, or `$import->update([...])` on them does nothing and the row's `status` field is the only thing that visibly changes.
