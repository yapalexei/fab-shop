# Prompt injection and the "lethal trifecta"

The risk model: an AI is dangerous when it combines (1) access to private data, (2) exposure to text an attacker can influence (a customer's email, a note, a line description), and (3) a way to send data out or change things. Remove any one leg and a successful injection has nowhere to go. We can't control what *other* tools the owner's AI client has (a browser, an inbox), so the defences below break the legs on our side. Don't weaken them without replacing them.

- **Where text an AI wrote can leave the shop.** The quote PDF prints `quote->notes`, every line `description`, and the customer's name, address and email, and `QuoteWorkflowController` mails it to `customer->email`. That is the real outbound channel, so it is what is gated. (The PDF/email views use escaped `{{ }}` and DomPDF's remote fetching is off; keep it that way.)
- **Read-only tokens by default (leg 3 per client).** A write needs a token created with the `mcp:write` ability (`McpTool::WRITE_ABILITY`); the owner ticks "allow changes" per token. `McpTool::shouldRegister()` hides write tools from a read-only token and `handle()` refuses them again, so it holds even if a tool is reached directly. Give read-only tokens to any AI that also browses the web or reads an inbox. Tokens made before this existed are read-only. `get-access` reports `token_can_change`.
- **Human review before anything AI-written can be sent (the outbound leg).** `quotes.ai_touched_at` / `customers.ai_touched_at` (`NeedsAiReview` trait; never fillable - only `markTouchedByAi()` sets it and only a person's `markReviewed()` clears it) are set by the MCP create/update quote and customer tools (a customer is flagged only when name, email, phone or address changes - notes stay internal). `QuoteWorkflowController::guardReviewed()` blocks `send`, `skipSend` and `resend` while the quote *or its customer* is flagged; `duplicate` carries the flag over so copying isn't a way round; saving the quote form does not clear it; the mark-reviewed routes (`quotes.ai-review`, `customers.ai-review`) are ordinary session-auth routes, so the agent's bearer token cannot call them. The quote follow-up draft withholds `to` when the customer is flagged. If you add another route that emails or exports quote/customer content, call the same guard.
- **No links, markup or hidden text written by an AI.** `McpTool::handle()` runs `UntrustedText::firstProblem()` over every argument of a write tool and refuses (logged as `blocked`) any string with a link/URL scheme, markdown link/image, HTML tag, or hidden/control character - central on purpose, so new tools can't forget. Ordinary text (brackets, parentheses, colons, "http" as a word) must keep passing; there is a test.
- **Text going to or from a model is cleaned.** `UntrustedText::clean()` strips zero-width, bidi-override and Unicode *tag* characters (U+E0000 block - invisible to a person, readable by a model) and control codes, and caps length; `cleanDeep()` is applied to everything an MCP tool returns, and `clean()` to the pasted email and quote data sent to a model. Output from the in-app drafters has markup stripped and links flagged (`QuoteDrafter`), and follow-up drafts return `warnings` for a link or an email address other than the customer's (`UntrustedText::warnings()`), shown in the dialog.
- **Unguessable fences.** `QuoteDrafter` and `QuoteFollowUpDrafter` wrap untrusted text in a random per-request tag (`<customer_message_xxxx>`, `<quote_xxxx>`) that the system prompt names, because a fixed tag can be closed by the attacker's own text. Prompts also tell the model the contents are data, not instructions - useful, but never the only defence.
- **Blast radius.** Writes are capped per hour per agent (`ai.mcp_writes_per_hour`, default 60; checked before the guard so injection attempts count), reads per minute (`ai.mcp_requests_per_minute`); least-privilege grants; no delete/cancel/send anywhere in `AgentAccess`. Refused attempts are logged (`mcp_requests.status` = `blocked`/`throttled`/`denied`) and the AI settings page shows recent AI activity and a count of blocked attempts so a manipulated session gets noticed.
- **Known open decision: `move-job` into Shipped / Invoiced is allowed.** Setting Invoiced stamps `invoiced_at`, puts the job in the dashboard's ready-to-invoice list and, if `Feature::QuickbooksSync` is ever switched back on, pushes an invoice to QuickBooks - an outward effect an injected instruction could trigger with only `jobs.update` and a write token. If QuickBooks is re-enabled, reconsider restricting AI moves into those two stages (or requiring review, as for quotes).
- **What this does not do.** It cannot make injection impossible, and it cannot see the owner's other connected tools. A write-capable token held by an AI that also reads untrusted email is still the dangerous combination; the UI says so and defaults away from it.

The owner manages it at `/shop/ai` (`ShopAiAgentController`, `McpConnectionPanel.tsx`; owner-only): turn on, choose what it can see and - in a collapsible roles-and-permissions-style matrix - what it can create and update (the form posts `permissions`, an array of `resource.action`), create a token (name + days, default `config('ai.mcp_token_days')`, never "no expiry"), revoke, turn off (deletes the agent and every token). A token's plaintext exists only as a one-time session flash (`new_token`) on the redirect after creating it - Sanctum stores a hash. Not built: OAuth (claude.ai and ChatGPT one-click connectors need it; bearer tokens work for Claude Desktop/Code and custom clients - `Mcp::oauthRoutes()` plus Passport is the documented route), a UI for the `mcp_requests` log, an undo for AI changes beyond the history entries, and an "accepted or not" signal on `ai_requests`.

Not built yet: the hosted-AI add-on, and the System 1 decision-model supplement (`DecisionModel` is still an unused interface).
