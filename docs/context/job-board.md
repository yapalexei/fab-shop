# Job board stages and moves

The board's columns are shop-configurable, not a fixed enum. `job_stages` is a per-shop, ordered (`position`) list: `App\Enums\JobStageRole` marks exactly three fixed rows - `NotStarted` (first), `Shipped`, `Invoiced` (last two) - that always exist and can't be renamed, reordered, or deleted (enforced server-side: `UpdateJobStageRequest::authorize()` blocks renaming a built-in, `JobStageController::destroy()` blocks deleting one). Everything between them is the shop's own custom stages (`role` null) - add/rename/delete/reorder from `/job-stages`, gated by the `job-stages.*` permissions (`ShopResource::JobStages`). Every shop starts with one generic starter stage, `App\Support\JobStages::STARTER_STAGE_NAME` ("Setup") - deliberately not named after a real fabrication step (a shop's actual process varies too much to presume: one cuts on a bandsaw, another on a CNC, neither of which is "welding"). `App\Support\JobStagePositions::renumber()` is the one place `position` values get assigned (a full renumber of the shop's custom stages on every create/reorder/delete) - no unique DB constraint on position, since app-level consistency is enough and a two-phase shuffle to satisfy one mid-reorder isn't worth it.

`Job::canTransitionTo(JobStage $target)`: any stage with a higher `position` is a legal forward move - skipping a stage a job doesn't need is allowed on purpose, not just single-step - and a backward correction is legal only while the job's current stage isn't `Shipped`/`Invoiced`. Cancellation isn't a stage any more - `Job::cancelled_at` (nullable timestamp, not fillable - set only via `JobStatusController::cancel()`, same pattern as `suspended_at`/`onboarded_at`) is a side flag orthogonal to whatever stage the job was at, so a cancelled job keeps its last real position instead of losing it to a terminal enum case. Reaching the `Shipped`-role stage flags a job as ready-to-invoice on the dashboard; reaching the `Invoiced`-role stage triggers the QuickBooks push (`PushJobInvoiceToQuickBooks`) and sets `invoiced_at` - both keyed off `JobStageRole`, never a stage's name, so renaming a stage can't break either.

Every status change - button or drag - goes through `JobMoveDialog` for confirmation first. Drag-and-drop (`@dnd-kit/core`, drag handle only so card links and touch-scrolling still work) is a per-shop setting, `shops.job_board_drag_enabled`, off by default (`config('shop.defaults.job_board_drag_enabled')`); the board only enables it for users with `jobs.update`. Moving needs `jobs.update`, cancelling `jobs.cancel` - checked in `JobStatusController` (a single `PATCH jobs/{job}/status` endpoint, `job_stage_id` for a move or `cancel: true` for cancellation, never both) since it depends on which one the request is.
