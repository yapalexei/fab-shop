# Security controls (sign-in, audit trail, headers)

Details and runbooks are in [docs/security.md](../security.md) - keep it current when a control changes. Things that aren't obvious from the code:

**Two-factor** is optional TOTP (`pragmarx/google2fa`, `App\Support\TwoFactor`). `LoginRequest::authenticate()` now only *checks* credentials and returns the `User` - it no longer signs in; `AuthenticatedSessionController` signs in directly, or parks the user id in the session and redirects to `TwoFactorChallengeController` when `hasTwoFactorEnabled()`. Don't go back to `Auth::attempt()` there: it would fire `Login` (and sign the user in) before the second factor. `verifyKeyNewer()` must be given `?? 0`, not null - with null the library returns a bare `true` instead of the step, nothing is stored and a code can be replayed (a test covers it). Recovery codes are stored as SHA-256 hashes, the secret is `encrypted`; both are `$hidden`, so they never reach Inertia's shared `auth.user`.

**Security log**: `App\Support\SecurityLog::record($what, $user, $props)` writes to the activity log under `log_name = 'security'` (no shop scoping - failed logins have no shop; the shop goes in `properties.shop_id`). `LogAuthenticationEvents` (registered in `AppServiceProvider`) covers login/logout/failed/lockout/password reset; controllers call it directly for access changes, invitations, AI connection/token changes, account deletion and every `PlatformAdminController` action. Never put a password, token, code or secret in the properties. New access-changing action = add a `SecurityLog::record()` call.

**Two-factor requirement** is policy, not a global switch - two-factor stays optional for anyone the policy doesn't cover. `App\Support\TwoFactorPolicy` resolves it: the platform default (`platform_settings.two_factor_required_roles` / `_grace_days` / `_policy_set_at`, edited at Platform admin > Security) applies to every shop unless the shop has its own (`shops.two_factor_required_roles` non-null; an empty list = "nobody", which is how a shop opts out). A person is covered when their role *in that shop* (read from Spatie's `model_has_roles`, not the team context) is in the list. Deadline = max(policy set-at, the date they joined the shop) + grace days, so a new teammate always gets the full period - that is why `Shop::members()/agents()` and `User::shops()` use `withTimestamps()` (pivot `created_at` was null for `attach()` before; legacy rows still are, and fall back to the policy date). `EnsureTwoFactorSetup` (web group, before `HandleInertiaRequests`) sets the `two_factor_requirement` request attribute that feeds the shared `twoFactorNotice` prop (dismissable banner, `SecurityNotices.tsx`, comes back daily) and, once overdue, redirects everything except profile / two-factor / logout / shop switch / legal pages to the profile. Policy columns are written with `forceFill` together with their set-at timestamp; re-saving identical values must not restart the countdown. Saving a policy dispatches `NotifyTwoFactorRequirement` (one email per person, earliest deadline). Owners edit theirs at Shop > Security > Two-factor sign-in (`/shop/security/two-factor`, owner-only).

**Security pages are indexes with sub-pages.** Shop: `/shop/security` (`shop.security.index`) links to Roles & permissions (`/shop/security/permissions`, route names `shop.permissions.*` unchanged), Two-factor sign-in (`/shop/security/two-factor`, `shop.security.policy`), the Audit log (`/shop/security/log`, `shop.security.log`) and, as a pointer, Shop settings (data export and deletion stay there); the nav has one "Security" entry that stays active across all of them (`SubPageLinks.tsx`, with `BackLink` on each sub-page). Platform admin: `/platform-admin/security` links to the two-factor default (`security.policy`) and the log (`security.log`). New security-related page = add a card to the index and a `BackLink` on the page.

**Security log pages**: `SecurityLogQuery` reads the `security` log for Platform admin > Security > Security log (everything) and Shop > Security > Audit log (owner-only). The shop view shows entries whose `properties.shop_id` is the shop (excluding `platform admin:` entries, which carry the *staff member's* shop) plus entries whose `target_shop_id` is the shop; failed logins have no shop so they stay platform-only.

**Shop data export and erasure** (Shop settings, owner-only via `manage-shop`): `App\Support\ShopData\TenantTables` discovers every table holding a shop's data by following foreign keys from `shops` (so a new table is covered automatically; `users`, `shop_user` and `consent_records` are excluded on purpose). Export = `BuildShopDataExport` (queued) writes one CSV per table + members + the uploaded files to a zip on the *default disk* (web and horizon don't share a filesystem), credentials excluded (`SKIP_TABLES`, any column matching token/secret/password/api_key/refresh), formula-looking cells prefixed with `'`; kept `shop.export_retention_days`, pruned daily. Deletion is requested with password + exact shop name, **scheduled** `shop.deletion_grace_days` out (everything keeps working, banner shown, members emailed, owner can cancel), then `app:purge-deleted-shops` (hourly) runs `PurgeShop`: files, history entries, rows deepest-first with a retry on `23503`/`23001` (Postgres reports RESTRICT as 23001), AI agent users. People's accounts are *not* deleted; the security log and consent records are kept. Adding a model with uploads: it is picked up if it implements `HasMedia` and lives in a discovered table.

**CSP**: `SecurityHeaders` sends a nonce-based policy (`config/security.php`, `CSP_MODE=enforce|report-only|off`) - scripts only from this site or with the request's nonce (`Vite::useCspNonce()`; `app.blade.php`'s inline scripts and Ziggy's `@routes` carry it - any new inline `<script>` needs `nonce="{{ Vite::cspNonce() }}"`), styles allow `'unsafe-inline'` (Radix/dnd-kit/Sonner set style attributes), `connect-src` includes the Reverb socket from `VITE_REVERB_*`, and the Vite dev server origin when running hot. Anything new from a third-party host (script, API, image CDN) must be added to the policy or it will be blocked - try it with `CSP_MODE=report-only` first and watch the browser console. The policy was tested by header/markup assertions only, not clicked through in a browser.

**Sessions and headers**: `AuthenticateSession` is in the `web` group (a password change signs other browsers out; in tests, a prior Sanctum `/mcp` call leaves `sanctum` as the default guard - `app('auth')->shouldUse('web')` before the next web request). `SecurityHeaders` adds nosniff/frame/referrer/permissions headers and HSTS over https; a CSP (below). Sessions are encrypted by default and `SESSION_SECURE_COOKIE=true` is set in `.railway/railway.ts`; local Sail runs over http, so leave it unset there. CI audits dependencies (`.github/workflows/security.yml`) - a new advisory fails the build.

The CSP also opens up to the feedback widget's instance origin (script/connect/frame/font) when `QUACKBACK_URL` is set - see [feedback-widget](feedback-widget.md).
